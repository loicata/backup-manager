## Synthèse — les risques majeurs (joyaux de la couronne)

Deux familles de bugs critiques menacent directement l'existence et la fiabilité des sauvegardes :

1. **Faux succès sur upload distant vide (« trou stage-5 », toujours ouvert).** Quand le listing distant revient vide, la vérification est *sautée* et le marqueur de commit est quand même écrit → un upload SFTP/S3 vide ou raté est journalisé comme **réussite**. Touche en production le profil chiffré **AWS S3** : depuis l'activation du chiffrement le 2026-05-28, **aucun** envoi AWS n'a été réellement contrôlé.

2. **Suppression du backup primaire déjà committé et vérifié.** Toute défaillance d'une phase *postérieure* au commit (échec d'un miroir, erreur de rotation, ou annulation utilisateur) déclenche `_best_effort_cleanup`, qui supprime sans condition le backup primaire **et son marqueur `.wbcommit`** — c'est exactement le mécanisme du « jour à zéro backup » du 2026-05-15 (deux fois dans la journée).

### [CRITIQUE] Empty remote file listing is silently treated as "verification skipped → success", masking a totally failed/empty SFTP or S3 upload (stage-5 mechanism, still live)

- **Statut :** ✅ CONFIRMÉ  |  **Catégorie :** data-loss  |  **Confiance audit :** high
- **Emplacement :** `src/core/backup_engine.py — 1388-1394 (also mirror twin 1839-1850)`

**Mécanisme.** _verify_remote tries verify_backup_files first; when it yields no checksums it falls to list_backup_files and does `if not remote_files: log('Remote verification skipped: backend does not support file listing'); return`. The empty-list branch is meant for backends that cannot enumerate, but for SFTP list_backup_files ALWAYS works (exec `find` or recursive SFTP) and returns [] ONLY when the backup directory is empty or missing; for an encrypted S3 archive it also returns [] (no objects under the prefix dir). There is no `len(remote_files) == len(ctx.files)` guard anywhere. This is the exact failure that produced the 2026-05-14 'Remote verification skipped: backend does not support file listing' line one second before the commit marker on the empty stage-5 backup; the POSIX helper fix prevents that specific empty-dir cause but the verify logic that lets an empty dir pass is unchanged.

- **Emplacement :** `src/core/run_history.py — 26-28, 94-114`

**Mécanisme.** Answering the primary question on run_history growth: the design is sound — append is O(1), a torn/corrupt last line (crash mid-append) is tolerated per-line at load (_parse_lines skips it with a debug log), rewrite() is atomic via .tmp + os.replace, and _MAX_ENTRIES_PER_PROFILE=50,000 protects the Tk Treeview. But the cap is enforced ONLY at load ('the file itself is not rewritten so append stays O(1)') — the on-disk file is never truncated or rotated. Cross-check vs the journal miner: run_history files are pure message streams (all level=info), correctly deleted with the profile, and contain none of the journal's status inconsistencies — the contamination issues live in the EventBus/per-run-log layer, not here.
